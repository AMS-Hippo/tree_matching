# Encoded partial-matching beam search

`FastBeamTreePathMatcher` is the specialized score-only implementation of the
partial-matching beam state space.  It is intended for the same two scoring
families as `FastTreePathMatcher`:

- `mode="equality"`: matching scalar labels receive their token weight;
- `mode="overlap"`: a node pair receives the largest positive weight of a
  token shared by the two labels.

The generic beam in `beam_align.py` remains the flexible implementation for
arbitrary Python scores, callbacks, stochastic exploration, bonuses, and
lookahead.  The fast implementation deliberately supports a smaller contract:

- deterministic score-only frontier priority;
- positive-token posting lists;
- finite `beam_width` and `expansion_width`;
- first-descendant selection within each token bucket;
- no custom callbacks, lookahead, random exploration, or heuristic bonuses.

## Reusable preparation

For repeated comparisons, fit one encoder on the complete corpus and prepare
each tree once:

```python
from path_matcher import FastBeamTreePathMatcher

matcher = FastBeamTreePathMatcher(
    mode="equality",
    beam_width=200,
    expansion_width=64,
    max_nodes_per_token_side=8,
)

matcher.fit_encoder(all_trees)
prepared = [matcher.prepare_tree(tree) for tree in all_trees]

path, score = matcher.predict_prepared(prepared[i], prepared[j])
```

Prepared trees cache:

- integerized labels or token sets;
- child arrays, depths, and subtree heights;
- DFS entry/exit intervals;
- per-token node postings in DFS order;
- the encoder fingerprint used to create the token ids.

Mixing prepared trees from different encoder fits raises an error.

## Candidate rule

At a live terminal pair, the implementation scans tokens from highest to lowest
weight.  For each token, it finds the strict descendants carrying that token in
both trees by binary search in the posting lists, takes at most
`max_nodes_per_token_side` nodes on each side, and forms their Cartesian
product.  The first `expansion_width` distinct pairs are retained.

In equality mode this reproduces the candidate ordering of the generic
`beam_partial_score` preset for the same budgets.  Randomized tests compare the
scores of the two implementations directly.

In overlap mode, candidates are generated by shared-token postings rather than
by buckets of complete token sets.  This is a different, usually more direct,
expansion rule.  It is still a valid Algorithm-7 partial-matching beam, but it
need not return the same approximate score as the generic overlap beam at
finite budgets.  A pair reached through several tokens receives the largest
shared-token weight because tokens are scanned in decreasing weight order.

## Exact limiting check

If the node cap, expansion budget, and beam width are large enough to retain
every positive feasible pair, the fast beam recovers the exact equality or
overlap optimum.  Permanent randomized tests compare this exhaustive limit
against `FastTreePathMatcher`.

## Diagnostics

Construct the matcher with `collect_diagnostics=True` and inspect
`last_diagnostics_`.  In addition to the common beam counters, the fast matcher
reports:

- token ranges scanned;
- posting-pair attempts;
- duplicate overlap pairs skipped;
- permanent retained-state pool size;
- whether Numba was available.

## Benchmark name

The reproducible benchmark preset is:

```text
fast_beam_partial
```

Its default budgets match `beam_partial_score`:

```text
beam_width = 200
expansion_width = 64
max_nodes_per_token_side = 8
max_token_types_per_expansion = 2048
```

The large rare-anchor sweep also contains a direct generic-versus-encoded
partial-beam implementation comparison.
